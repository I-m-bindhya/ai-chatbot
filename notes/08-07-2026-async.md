1. When should you use async?
Use async for I/O-bound operations, not CPU-bound computations.

2. Async propagates upward.

A useful rule you'll see in production codebases:

CPU work → def
I/O work → async def

Don't make everything async "just because."

3. What is the difference between async and streaming?

Async allows the server to handle multiple I/O operations concurrently without blocking.
Streaming sends partial results to the client as they become available, improving perceived responsiveness.
They complement each other: async improves server scalability, while streaming improves user experience.

4. Why should title generation be a background task?

Title generation is not required to answer the user's request. Running it in the background reduces response latency while keeping the user experience unchanged. It's an example of moving non-critical work off the request path.


5. Why should token accounting be implemented inside the provider layer instead of the agent layer?

The provider layer has direct access to model-specific metadata such as prompt tokens, completion tokens, latency, and model identifiers. Keeping token accounting in the provider allows the agent to remain provider-agnostic and supports swapping providers without changing business logic.

## Why Async?

LLM calls are I/O-bound operations.

Instead of blocking one request at a time:

```text

↓

↓

```

The server can process multiple requests concurrently:

```text
User A ──────────────┐
                     │
User B ───────┐      │
              │      │
User C ───┐   │      │
```

* FastAPI routes
* ChatService
* AgentOrchestrator
* RouterAgent
* Specialized agents
* AIAgent
* PlanningService
* ReflectionService
* OllamaProvider

---

## Interview Question

**Q:** Why use async for AI applications?

**Answer:**

AI applications spend most of their time waiting for external services (LLMs, vector databases, APIs). Async allows the server to handle many requests concurrently while waiting for these operations to complete.

# 6. Token Accounting

## Goal

Every provider call should return:

```python
AIResponse(
    answer="...",
    usage=TokenUsage(...)
)
```

---

## TokenUsage

```python
TokenUsage

model

prompt_tokens

completion_tokens

total_tokens

latency_ms
```

---

## Provider Responsibility

The provider measures:

* Prompt tokens
* Completion tokens
* Total tokens
* Latency
* Model name

The provider should **not** aggregate usage across multiple model calls.

---

## Agent Responsibility

The agent aggregates usage from:

* Planning
* Tool loop
* Final response
* Reflection
* Improvement

This produces **request-level usage**.

---

## Architecture

```text
Provider

↓

Call Usage

↓

Agent

↓

Request Usage
```

---

## Important Design Lesson

There are two different concepts:

### Call Usage

One LLM invocation.

Example:

```text
Planning

120 tokens
```

---

### Request Usage

Multiple LLM invocations.

Example:

```text
Planning

120

↓

Reflection

80

↓

Improve

100

↓

Total

300
```

Never mix these responsibilities.

---

## Interview Question

**Q:** Why should token accounting live in the provider?

**Answer:**

The provider has direct access to model-specific metadata such as prompt tokens, completion tokens, latency, and model identifiers. Keeping accounting inside the provider keeps the agent provider-agnostic.

# Key Design Principles Learned

* Separate business logic from infrastructure.
* Keep providers provider-agnostic.
* Use async for scalability.
* Use background tasks for non-critical work.
* Design streaming as a separate execution path.
* Measure usage per model call, aggregate per request.
* Prefer logging over print statements.
* Configuration belongs outside business logic.
